# orbital-compiler — open gaps

Every open gap this repo owns lives here. This file is the source of truth; the monorepo's `docs/Almadar_Gaps.md` only rolls it up.

- **One entry per gap:** `- **<code>** — <what is wrong and where>. <owning package> [mechanical|architectural] — <evidence, prevention rung>`.
- **Codes:** new gaps use this repo's prefix `G-ORBITAL-COMPILER-`. Take the "Next code" below, then bump it in the same edit. Codes are never reused or renamed.
- **Close by deleting.** Remove the entry in the same commit as the fix.

Next code: `G-ORBITAL-COMPILER-019`

- **G-ORBITAL-COMPILER-018** [mechanical] — `orb validate` passes a program whose client projection fails `ORB_X_OPERATOR_ARG_UNDETERMINED`. An orbital whose only page is a protocol endpoint (`page boot`) is left out of the client program (EXEC-ENDPOINT-5), and its entities leave with it. A route page in another orbital that reads that entity (a fetch success typed `{ data : [SketchRound]! }`) then has untyped rows on the client, and the client step of `orb fleet deploy` refuses it. Source and resolved validate never judge the client projection. Found 2026-11-23 deploying Tukaj Lej: `family-sketch-chain`'s Play and `family-events`' Upcoming were refused 17 times. Typing the reads with structural row aliases only moved the failure (`OIR_ERROR … Fetch entity 'SketchRound' does not exist`). Worked around by declaring `SketchRound` and `FamilyEvent` in the app's own route-page data orbital (`FamilyData`) and having the atoms `expects entity` them. Fix: validate judges the client projection too, or the projection keeps the entity types its client traits read. Reproduce: an endpoint-only orbital with an entity, and a route page in another orbital that fetches it with a payload typed by that entity, then `orb fleet deploy --target local`. Prevention rung: (2) `orb validate`, one verdict for every projection it ships. Severity: medium. Root cause: H3.

- **G-ORBITAL-COMPILER-017** [mechanical] — A call-site `only { … }` that names traits by their atom-local names (`AssistantThread`) when the composed orbital's traits carry resolved names (`FamilyHelperAssistantThread`) silently keeps no trait at all: the orbital resolves with empty pages, and validate reports only downstream fallout (unresolved listen sources, unreferenced merged fields), never the unknown names. Found 2026-11-23 composing `family-helper`'s `FamilyHelper` into `tukaj-lej.lolo`. Fix: `only` (and `omit`) refuse a name no trait of the composed orbital has, listing the names it does have. Reproduce: `orbital X = Helper.orbitals.FamilyHelper { only { AssistantThread } }`, then validate. Prevention rung: (2) `orb validate`. Severity: medium. Root cause: one-off.

- **G-ORBITAL-COMPILER-016** [owner-decision] — `orb validate` on a `.lolo` source passes while the program it resolves to fails `ORB_I18N_KEY_UNTRANSLATED`. `orb resolve` unions the app's `locales` with every composed atom's (`loader::composed_locales`; the Rasm atoms declare `[en, ar, sl]`), so an app that declares `[en, sl]` resolves to `[en, sl, ar]`, and the compiled client then demands an `ar` catalog for every key. Source validate never checks catalogs against the resolved set. Found 2026-11-23 deploying Tukaj Lej (`family/organisms/tukaj-lej.lolo`) to the local fleet: the client step refused 8 keys. The two checks contradict each other: with an `ar` catalog added, source validate refuses it (`ORB_I18N_CATALOG_INVALID`: a catalog for a locale the app does not declare), and without it the resolved program fails. So the only state both accept is declaring `ar` too. Worked around by declaring `locales: [en, sl, ar]` (an Arabic route the owner did not ask for). Two questions: rung 2, should source validate judge catalogs against the resolved locales (one verdict for source and resolved program)? Owner call, should an app's own `locales` bound the union, so composing a std atom never adds a language the app did not declare (EXEC-BOUND-3, nothing implicit)? Reproduce: declare `locales: [en, sl]` in an app composing std-rasm-page, validate the source (clean), then `orb resolve` it and validate the result. Severity: medium. Root cause: H3.

- **G-ORBITAL-COMPILER-015** [mechanical] — The `set` type check (`phases/validation/expressions/effect/set.rs`, `ORB_X_SET_RETURN_TYPE_MISMATCH`) judges the same expression on the same entity differently once the trait comes from an atom by `-> Entity` rebind. `std-realtime-chat`'s inline `DirectMessageStarter -> ChannelMember` validates `AUTO_OPEN … (set @entity.openChannel (object/get (array/reduce ?data …) channel))` (`openChannel : string`, `channel : Channel`). The same trait lifted into a std atom over its own member entity and composed as `trait DirectMessageStarter = Conversation.traits.DirectConversationStarter -> ChannelMember` is refused: "set @entity.openChannel (type 'string') is assigned a value that evaluates to 'Channel?'". One of the two answers is wrong: either a relation read may be written into a `string` field (the inline pass is right and the rebound path resolves the payload or field types differently), or it may not (the inline pass is a false negative). Found 2026-11-23 while converging std-realtime-chat's chat data onto std-conversation (G-BEHAVIORS-193): this blocks lifting DirectMessageStarter, so it stays inline. Reproduce: lift DirectMessageStarter into `std-conversation.lolo` over a `ConversationMember` entity, rebind it at the std-realtime-chat call site with the original listens, and validate std-realtime-chat. Prevention rung: (2) orb validate: one type judgement per expression whatever path composed the trait, pinned by a twin test (inline and rebound give one verdict). Severity: medium. Root cause: H3.

- **G-ORBITAL-COMPILER-014** [mechanical] — The config shape check refuses a knob value that its declared union type allows: a knob typed `{ anchor : "cwd" | "exe-dir" | { env : string! }!, path : string! }` (std-chrome's `ChromePath`, the shape every anchored-path knob uses) answers `ORB_T_CONFIG_SHAPE_MISMATCH ... anchor: expected string, got object` for `{ anchor: { env: "HOME" }, path: ... }`, so no composer can anchor a path to an environment variable through a config knob. Found 2026-11-13 composing std-chrome into std-orb-profile (worked around by anchoring Chrome's profile to cwd under .orbital/profile) and in std-samply's first draft. Since 2026-11-21 it also blocks the owner's ruling that orb keeps its working folders under `~/.almadar`: `orb serve` and the launchpad moved, but std-orb-profile, std-guest-e2e and std-guest-real-sweep still put their Chrome profiles and reports in `<cwd>/.orbital/` until this lands (then anchor them `{ env: "HOME" }` under `.almadar/profile` and `.almadar/guest-e2e`). Reproduce: set std-chrome's profileDir to `{ anchor: { env: "HOME" } path: "x" }` in a composer and validate. Prevention rung: (1) the type system: the config check must read the union the knob declares, the same way an emit payload check does. Severity: medium. Root cause: one-off.

- **G-ORBITAL-COMPILER-012** [mechanical] — A `persist` row may carry a key its entity does not declare when the row is built with `object/merge`: std-crm-experience `NotePersistor` (`persist create Note (object/merge ?data { author: …, createdAt: … })`, `experience/organisms/std-crm-experience.lolo:793`) and std-field-service-experience (`persist create WorkOrderRow`, line 371) write `createdAt` into entities that declare no `createdAt`, and both validate 0/0. - **G-ORBITAL-COMPILER-011** — `inline::drop_unreferenced_colliding_auxiliaries` decides whether an auxiliary entity that collides with another orbital's primary is still referenced by serializing the orbital's whole trait list to JSON and substring-searching it for the entity name (`trait_blob_mentions`): a text-matching heuristic (a name inside a string literal or description keeps the entity; a reference spelled any other way drops it). - **G-ORBITAL-COMPILER-009** [mechanical] — A type guard does not narrow: `(if (validate/string @t) (as @t string) …)` types the `as` branch `string?`, because `as` is a checked narrowing that is null on mismatch and `validate/string` proves nothing to it, so a guarded read can never be non-null without a hand-written null check (found 2026-11-07 fixing G-STD-293: `packages/almadar-std/behaviors/lolo/ui/core/atoms/std-tag-strip.lolo:46` and five more arms now spell `(let ((s : string? (as @t string))) (if (= @s null) … [@s]))`). Fix: `validate/<type>` guards narrow their operand in the true branch (inference `presence`/narrowing), so `(as @t string)` under that guard is `string`. Rung: (1) the type system. Severity: medium. Root cause: A4.
